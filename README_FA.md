# Incentive Lab — پروژه نمونه‌کار Data Science برای بهینه‌سازی مشوق‌های Supply

[English README](README.md) · [شرح کامل پروژه](docs/project_description_fa.md) · [راهنمای مصاحبه](docs/interview_guide_fa.md) · [راهنمای انتشار در GitHub](docs/publish_to_github_fa.md)

**مسئله:** چطور بفهمیم یک کمپین مشوق واقعاً سفر افزایشی ایجاد می‌کند، از نظر اقتصادی می‌ارزد، و برای کمپین بعدی چه جامعه‌ای را باید وارد آزمایش کنیم؟

> **مهم:** این یک پروژه نمونه‌کار مستقل و آموزشی با الهام از مسئله‌ی مشوق‌های عرضه در یک بازارگاه است؛ وابسته به اسنپ نیست و از طرف آن تأیید نشده است. تمام داده‌ها مصنوعی‌اند؛ هیچ اتصال یا دسترسی به سامانه‌ها و داده‌های واقعی اسنپ وجود ندارد و اعداد این پروژه عملکرد واقعی شرکت نیستند.

## مستند اصلی پروژه

- معرفی کامل پروژه، مسئله کسب‌وکار، طراحی آزمایش، فرهنگ داده، KPIها، مدل‌سازی، معماری، نتایج نمونه و محدودیت‌ها: `docs/project_description_fa.md`
- نسخه قابل ویرایش Word همین مستند: `docs/project_description_fa.docx`
- راهنمای مصاحبه: `docs/interview_guide_fa.md`

## چه چیزی تحویل داده شده؟

1. **داده‌ساز قابل تکرار:** ۱۲٬۰۰۰ ردیف آزمایش تصادفی و یک جامعه مستقل ۳٬۰۰۰ راننده‌ای برای امتیازدهی، با seed ثابت.
2. **تحلیل آماری:** اختلاف میانگین درمان و کنترل، فاصله اطمینان ۹۵٪، آزمون Welch و تحلیل اکتشافی منطقه/بازه زمانی.
3. **اقتصاد کمپین:** ROI و ارزش خالص سناریویی با فرض قابل‌تغییر حاشیه سود هر سفر؛ همراه با تحلیل حساسیت و نقطه سربه‌سر.
4. **مدل پیش‌بینی uplift:** T-learner با دو مدل Random Forest جدا برای پیامد مشوق و کنترل، ارزیابی روی holdout و بررسی نتیجه‌ی طبقات امتیاز.
5. **امتیازدهی جامعه مستقل:** رتبه‌بندی ۳٬۰۰۰ راننده‌ی مصنوعی بدون استفاده از پیامد آینده‌ی آن‌ها؛ ۲۰٪ بالای رتبه برای بررسی در آزمایش بعدی.
6. **API:** سرویس FastAPI با endpointهای `/health`، `/score` و `/score/batch`.
7. **کنترل کیفیت داده:** بررسی schema، missing value، تکرار شناسه، بازوهای آزمایش، هزینه‌ها، نرخ‌ها، ردیف‌های مصنوعی و جلوگیری از ورود پیامدهای بعد از درمان به جامعه امتیازدهی؛ گزارش در `project_outputs/data_quality_report.json`.
8. **بررسی آماری تکمیلی:** رگرسیون OLS با ویژگی‌های پیش از درمان و خطای استاندارد مقاوم HC3 به‌عنوان بررسی ثانویه؛ اثر خام حاصل از تصادفی‌سازی همچنان معیار اصلی گزارش است.
9. **SQL و عملیات:** اسکیمای مرجع SQL Server، کوئری‌های A/B و بخش‌ها، الگوی پایش، snapshot آزمایشی drift و راهنمای چرخه عمر مدل. SQLها مرجع‌اند و هنوز روی دیتابیس واقعی اجرا نشده‌اند.
10. **API و داشبورد:** FastAPI با endpointهای `/health`، `/score` و `/score/batch`؛ `snapp_incentive_dashboard_v3.html` داشبورد standalone تعاملی است و با خروجی جاری pipeline همگام می‌شود.
11. **نمودار و تست:** چهار نمودار تحلیلی در `project_outputs/figures/` و تست‌های خودکار برای داده‌سازی، تحلیل، پایش و API.

## اجرای سریع در Windows

در ریشه‌ی پوشه‌ی پروژه (جایی که این فایل قرار دارد):

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
python -m src.run_pipeline
```

اجرای خط لوله، داده‌ها را می‌سازد، تحلیل آزمایش را انجام می‌دهد، مدل را آموزش می‌دهد، داشبورد HTML را با خروجی‌های جدید همگام می‌کند و فایل مدل را در `artifacts/uplift_model.joblib` ذخیره می‌کند. خروجی‌های اصلی در `project_outputs/` قرار می‌گیرند. در صورت اجرای جداگانه‌ی اجزای خط لوله، می‌توانید داشبورد را با `python -m src.sync_dashboard` همگام کنید.

اجرای تست‌ها:

```powershell
python -m pytest -q
```

اجرای API محلی پس از آموزش مدل:

```powershell
uvicorn api.app:app --reload
```

سپس `http://127.0.0.1:8000/docs` را باز کنید. برای container، ابتدا pipeline را اجرا کنید تا artifact ساخته شود و سپس `docker build -t incentive-lab .` و `docker run -p 8000:8000 incentive-lab` را اجرا کنید.

## KPIها و تعریف مالی

- **اثر اصلی:** `ATE = میانگین سفر درمان − میانگین سفر کنترل`.
- **فاصله اطمینان:** فاصله ۹۵٪ Welch برای اختلاف میانگین‌ها؛ p-value به تنهایی معیار تصمیم نیست.
- **هزینه هر سفر افزایشی:** میانگین هزینه‌ی دریافت‌کنندگان مشوق تقسیم بر افزایش سفر مشاهده‌شده، فقط وقتی lift مثبت باشد.
- **ROI سناریویی:** `(ATE × حاشیه سود فرضی هر سفر − میانگین هزینه مشوق) ÷ میانگین هزینه مشوق`.

پیش‌فرض حاشیه سود هر سفر ۵۰٬۰۰۰ تومان است و فقط برای شبیه‌سازی استفاده می‌شود. در تصمیم واقعی باید تعریف مصوب contribution margin و محدودیت‌های بودجه از تیم Finance گرفته شود.


## نمونه خروجی اجرای قابل‌بازتولید

در اجرای فعلی با `seed=42`، داده مصنوعی شامل ۱۲٬۰۰۰ راننده در آزمایش (۵٬۸۹۹ مشوق و ۶٬۱۰۱ کنترل) و ۳٬۰۰۰ راننده مستقل برای امتیازدهی ساخته شد. نتایج زیر صرفاً برای نمایش قابلیت pipeline هستند:

| معیار | خروجی نمونه | برداشت درست |
|---|---:|---|
| اثر متوسط سفر (ATE) | +۱٫۹۹۶ سفر به‌ازای راننده تخصیص‌یافته | فاصله اطمینان ۹۵٪: ۱٫۶۲۶ تا ۲٫۳۶۵؛ داده مصنوعی |
| ROI سناریویی | +۱۶٫۵٪ | مبتنی بر فرض حاشیه سود ۵۰٬۰۰۰ تومان برای هر سفر افزایشی، نه نتیجه مالی واقعی |
| نقطه سربه‌سر حاشیه سود | حدود ۴۲٬۹۳۵ تومان/سفر | یک ورودی تصمیم سناریویی است |
| جمعیت ۲۰٪ بالای امتیاز | ۶۰۰ راننده | برای آزمایش بعدی؛ نه لیست قطعی دریافت‌کنندگان مشوق |
| کنترل کیفیت مصنوعی | PASS | فقط صحت پایه داده تولیدشده را نشان می‌دهد |

**محدودیت مهم مدل:** در holdout، اثر مشاهده‌شده در ۲۰٪ بالای امتیاز حدود ۲٫۴۱ سفر بود، اما فاصله اطمینان آن گسترده است (حدود ۰٫۶۷ تا ۴٫۱۴) و میانگین uplift پیش‌بینی‌شده بالاتر (حدود ۴٫۴۷) بود. این فاصله، نشانه‌ی نیاز به کالیبراسیون و آزمون سیاست هدف‌گیری است؛ بهبود علّی یا صرفه‌جویی تضمین‌شده اثبات نشده است.

## خروجی‌های قابل بررسی

- `project_outputs/experiment_summary.csv`: اختلاف میانگین و آزمون‌های A/B.
- `project_outputs/segment_summary.csv`: نتایج اکتشافی منطقه و بازه زمانی.
- `project_outputs/campaign_economics.json` و `economics_sensitivity.csv`: اقتصاد سناریویی و حساسیت به حاشیه سود.
- `project_outputs/model_validation.json`: معیارهای holdout به تفکیک بازو و نتیجه‌ی score bandها.
- `project_outputs/uplift_recommendations.csv`: ۶۰۰ ردیف منتخب از ۳٬۰۰۰ نامزد، با امتیاز پیش‌بینی‌شده.
- `project_outputs/adjusted_effect_check.json`: رگرسیون تعدیل‌شده ثانویه.
- `project_outputs/data_quality_report.json`: کنترل‌های کیفیت داده.
- `project_outputs/monitoring_snapshot.json`: snapshot آفلاین drift؛ نه پایش آنلاین.
- `project_outputs/figures/`: نمودارهای اثر، هزینه‌ی بخش‌ها، اعتبارسنجی score band و حساسیت ROI.

## نکات علمی و محدودیت‌ها

- پیامدهای بعد از تخصیص وارد ویژگی‌های مدل نشده‌اند تا نشت اطلاعات رخ ندهد.
- ارزیابی مدل با یک تقسیم تصادفی ۸۰/۲۰ انجام می‌شود؛ هنوز میانگین چند seed یا اعتبارسنجی خارج از زمان نداریم.
- امتیاز uplift فردی اثر علّی قطعی نیست. برای اثبات برتری سیاست هدف‌گیری باید تست آینده‌نگر تصادفی در score bandها اجرا شود.
- تحلیل بخش‌ها اکتشافی است؛ قبل از تصمیم rollout باید توان آماری، آزمون‌های چندگانه، اثر بر سایر کاربران بازار و guardrailها ارزیابی شوند.
- SQLها با dialect مربوط به SQL Server نوشته شده‌اند اما روی دیتابیس واقعی اجرا نشده‌اند؛ نیازمند mapping به warehouse، بررسی دسترسی و بارگذاری داده‌اند.
- drift snapshot فقط آزمایشی است؛ به ترافیک آنلاین و پیامدهای بالغ‌شده متصل نیست.
